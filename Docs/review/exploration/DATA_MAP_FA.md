# نقشهٔ اولیهٔ داده

این نقشه برای شناخت داده است. کلیدهای زیر پیشنهادی هستند و هنوز همهٔ آن‌ها آزمون یکتایی نشده‌اند.

| گروه | فایل‌ها | هر ردیف چه چیزی است؟ | کلید یا ارتباط احتمالی |
|---|---|---|---|
| سفارش | orders | یک سفارش | order_id |
| رخداد سفارش | order_events | یک مرحله یا تغییر سفارش | order_id به سفارش وصل می‌شود؛ به کلید مرکب نیاز دارد |
| تیکت | tickets | یک تیکت پشتیبانی | ticket_id؛ order_id ارتباط با سفارش است |
| رخداد تیکت | ticket_events | یک رخداد تیکت | ticket_id به تیکت وصل می‌شود |
| رضایت | csat | یک پاسخ نظرسنجی | ticket_id به تیکت وصل می‌شود؛ یکتایی پاسخ باید بررسی شود |
| فروش سازمانی | crm_leads | یک سرنخ | lead_id |
| رخداد فروش سازمانی | crm_lead_events | تغییر مرحله یا اصلاح ارزش قرارداد | lead_id؛ اصلاح ارزش، سرنخ جدید نیست |
| بازاریابی | mkt_daily | آمار یک منبع در یک روز | نامزد کلید: date و source |
| بازدید | web_sessions | آمار یک کانال در یک روز | نامزد کلید: date و channel |
| وظیفه | tasks | یک وظیفه با مالک و تیم | task_id؛ owner_id و team_id |
| رخداد وظیفه | task_events | یک تغییر وضعیت وظیفه | task_id به وظیفه وصل می‌شود |
| ظرفیت | staff_availability | وضعیت دسترس‌پذیری یک فرد در یک روز | نامزد کلید: شناسهٔ فرد و تاریخ؛ دادهٔ محدود |
| سازمان | units، teams، managers، staff | یک واحد، تیم، مدیر یا فرد | شناسهٔ موجودیت؛ تاریخ شروع نیز مهم است |
| دسترسی | access_matrix | دامنهٔ دسترسی یک مدیر | manager_id؛ چند موجودیت در یک خانه آمده‌اند |
| تنظیمات | kpi_dictionary، workflow_definitions، escalation_rules، monthly_targets | تعریف شاخص، مرحله، قاعده یا هدف | دادهٔ تنظیمات؛ با تراکنش‌ها فرق دارد |
| تقویم | calendar_days، events_calendar | یک روز یا رویداد زمینه‌ای | تاریخ؛ برای تعطیلات و خط پایه |
| حافظه | decisions_history | یک تصمیم گذشته | برای پیگیری اثر تصمیم |
| گزارش قدیمی | legacy_weekly_sales_report_by_sales_team | مقدار گزارش فروش با تعریف قدیمی | تعریف آن باید جداگانه تطبیق داده شود |

## ترتیب بررسی بعدی

1. معنای هر ستون و واحد مبلغ یا زمان را از README و SQL مرجع ثبت کنیم.
2. یکتایی کلیدها و کلیدهای مرکب رویدادها را بررسی کنیم.
3. زمان رخداد، زمان دریافت و تاریخ اثر تنظیمات را جدا کنیم.
4. سیاست رکورد تکراری، اصلاحیه و منبع غایب را مشخص کنیم.
5. ERD را از ارتباط‌های تأییدشده بسازیم.
6. EDA را روی دادهٔ استانداردشده انجام دهیم؛ روندها و تغییر شاخص‌ها پس از این مرحله بررسی شوند.

فایل‌های خام در این بررسی تغییر نکرده‌اند. هیچ شاخص کسب‌وکار یا علت رویداد هنوز تأیید نشده است.
