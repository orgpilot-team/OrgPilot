> **Tag ثابت:** `DIDRAH-ARCH-CONTROL-V3`

## ۱. هدف سند

این فایل مرجع فعال تصمیم‌ها و مسائل معماری دیدراه است.

در نسخه ۳:

- تصمیم‌های مرتبط در یک ADR ادغام شده‌اند.
- شماره ADRها و مسائل از نو تعیین شده‌اند.
- شماره‌های قدیمی در جدول ردیابی حفظ شده‌اند.
- موضوعات بسته از مسائل باز جدا شده‌اند.
- بخش‌های کنترل اجرا و شناسه‌های `AT-*` وجود ندارند.

## ۲. ترتیب اعتبار منابع

در صورت تعارض، این ترتیب استفاده شود:

1. پاسخ رسمی برگزارکننده؛
2. بریف پروژه؛
3. قراردادهای ماشین‌خوان دیتاست؛
4. تصمیم ثبت‌شده تیم؛
5. اسناد معماری.

## ۳. وضعیت‌ها

| وضعیت | معنی |
|---|---|
| `پذیرفته‌شده` | تصمیم قطعی است. |
| `باز` | تصمیم یا قرارداد لازم هنوز مشخص نیست. |
| `تصمیم‌شده؛ اجرا لازم` | تصمیم قطعی است، ولی فایل یا پیاده‌سازی هنوز هماهنگ نشده است. |
| `پیشنهادی` | راهکار وجود دارد، ولی هنوز تصویب نشده است. |
| `بسته` | مسئله تصمیمی حل شده است. |

## ۵. تصمیم‌های معماری

### ADR-V3-01 — معماری یکپارچه ورود و آماده‌سازی داده

- **وضعیت:** پذیرفته‌شده.
- **ادغام‌شده از:** `ADR-02`، `ADR-03`، `ADR-08`، `ADR-11`، `ADR-16` و `ADR-19` نسخه ۲.
- **موضوع:** دریافت فایل، قرارداد Schema، پاک‌سازی، کیفیت، تکرار، تعارض، ذخیره استاندارد و Snapshot.

#### ۵.۱. مسیرها و ترتیب اجرا

- مسیر ورودی فقط از `DATA_DIR` خوانده می‌شود.
- مسیر خروجی فقط از `OUTPUT_DIR` خوانده می‌شود.
- مسیر ثابت در کد مجاز نیست.
- Dropها از `day_000` تا `day_090` به‌ترتیب پردازش می‌شوند.
- `manager_inputs` و `uploads` در روز ثبت‌شده پردازش می‌شوند.

#### ۵.۲. مرز زمانی

- گزارش صبح روز D فقط داده‌ها و ورودی‌های معتبر تا پایان روز D-1 را می‌بیند.
- ورودی مدیر در روز D نخستین بار در گزارش صبح D+1 اثر می‌گذارد.
- Upload روز D پس از کنترل، از گزارش صبح D+1 قابل استفاده است.
- تغییر سازمانی M11 در روز ۷۵ از گزارش صبح روز ۷۶ اعمال می‌شود.
- فایل آماده‌نشده یا رویداد آینده در تحلیل روز جاری استفاده نمی‌شود.

#### ۵.۳. قالب‌های ورودی

- CSV برای داده ساختاریافته استفاده می‌شود.
- JSON برای Manifest، ورودی مدیر و قراردادها استفاده می‌شود.
- Markdown برای متن عرضه‌شده استفاده می‌شود.
- Excel و PDF بدون قرارداد رسمی پشتیبانی نمی‌شوند.
- سیستم قالب فایل را حدس نمی‌زند.
- فایل بیرونی داده است، نه دستور.

#### ۵.۴. Source Intake

برای هر فایل این اطلاعات ثبت می‌شوند:

- مسیر نسبی؛
- Source؛
- روز Drop؛
- زمان دریافت؛
- Hash؛
- وضعیت Manifest؛
- وضعیت پردازش؛
- دلیل رد یا قرنطینه.

#### ۵.۵. Schema Registry

هر منبع یک قرارداد نسخه‌دار دارد. قرارداد شامل این موارد است:

- نام فایل؛
- ستون‌های اجباری؛
- نام استاندارد هر ستون؛
- نام‌های جایگزین ستون؛
- نوع داده؛
- قالب؛
- واحد؛
- امکان خالی‌بودن؛
- مقدارهای مجاز؛
- کلید اصلی؛
- رفتار خطا.

اگر ساختار فایل تغییر کند، نسخه جدید Schema ساخته می‌شود. Dropهای قدیمی با Schema زمان خود خوانده می‌شوند.

#### ۵.۶. نگاشت نام ستون‌ها

- `tickets.created_at` و `tickets.create_time` هر دو به `tickets.created_at` تبدیل می‌شوند.
- `ticket_events.at` و `ticket_events.event_time` هر دو به `ticket_events.event_time` تبدیل می‌شوند.
- نام ناشناخته بدون قرارداد رسمی پذیرفته نمی‌شود.

#### ۵.۷. Normalizer

Normalizer این کارها را انجام می‌دهد:

1. نام ستون را به نام استاندارد تبدیل می‌کند.
2. متن، عدد و تاریخ را به نوع استاندارد تبدیل می‌کند.
3. واحد و قالب را یکسان می‌کند.
4. مقدار خالی را طبق قرارداد منبع نگه می‌دارد.
5. مقدار حدسی یا ساختگی تولید نمی‌کند.

#### ۵.۸. Data Quality

- فایل غایب از صبح اول با `missing` گزارش می‌شود.
- تا زمان ورود فایل، `missing` هر صبح تکرار می‌شود.
- KPI وابسته به منبع غایب `null` است.
- ورود دیرهنگام یک بار با `late_arrival` گزارش می‌شود.
- داده دیررسیده موجب بازسازی کامل می‌شود.
- خطای داده Signal کسب‌وکار نیست.
- فایل دارای ستون اجباری گمشده وارد Snapshot معتبر نمی‌شود.
- ردیف نامعتبر با علت روشن قرنطینه می‌شود.

#### ۵.۹. تکرار و تعارض

- ردیف کاملاً یکسان بر اساس کلید اصلی فقط یک بار محاسبه می‌شود.
- کلیدهای اصلی عبارت‌اند از `order_id`، `ticket_id`، `lead_id` و `task_id`.
- کلید رویداد ترکیب شناسه، نوع رویداد و زمان است.
- تکرار با `type: duplicate` گزارش می‌شود.
- دو Payload متفاوت با کلید یکسان خودکار ادغام نمی‌شوند.
- Payloadهای متعارض همراه با Source، Drop، Hash و زمان دریافت قرنطینه می‌شوند.
- رکورد متعارض وارد Snapshot معتبر نمی‌شود.
- KPI وابسته به رکورد متعارض تا رفع تعارض `null` است.
- آخرین ردیف خودکار معتبر فرض نمی‌شود.

#### ۵.۱۰. Canonical Storage

- داده معتبر با نام ستون و نوع استاندارد ذخیره می‌شود.
- داده خام و داده استاندارد از یکدیگر جدا می‌مانند.
- هر رکورد استاندارد به فایل، Drop و Hash منبع پیوند دارد.
- داده قرنطینه‌شده وارد محاسبه نمی‌شود.

#### ۵.۱۱. Daily Snapshot و بازسازی

- هر گزارش از یک Snapshot ثابت استفاده می‌کند.
- ورود داده در میانه Run نتیجه همان Run را تغییر نمی‌دهد.
- پس از داده دیررسیده، اصلاح‌شده یا رفع تعارض، همیشه بازسازی کامل انجام می‌شود.
- محاسبه انتخابی KPI در نسخه اول انجام نمی‌شود.
- محاسبه انتخابی فقط در صورت مشکل زمان اجرا و به‌عنوان بهینه‌سازی آینده مجاز است.

#### ۵.۱۲. افزودن منبع جدید

- Schema منبع در Registry ثبت می‌شود.
- در صورت نیاز، مبدل مخصوص قالب منبع اضافه می‌شود.
- مراحل اصلی Intake، پاک‌سازی، کیفیت، Snapshot و KPI تغییر نمی‌کنند.

### ADR-V3-02 — محاسبه و ردیابی KPI

- **وضعیت:** پذیرفته‌شده؛ قرارداد عدد موردی باز است.
- **ادغام‌شده از:** `ADR-01` و بخش عددی `ADR-09` نسخه ۲.
- **موتور محصول:** PostgreSQL است.
- **مرجع صحت:** عدد مرجع هر KPI با اجرای SQL فرهنگ شاخص‌ها روی SQLite محاسبه می‌شود.
- نتیجه PostgreSQL باید با نتیجه مرجع SQLite یکسان باشد.
- **میانه:** `median()` در SQLite به `percentile_cont(0.5)` در PostgreSQL تبدیل می‌شود. استفاده از `percentile_disc` مجاز نیست.
- **فاصله زمانی:** `julianday(b) - julianday(a)` در SQLite فاصله را بر حسب روز برمی‌گرداند.
- در PostgreSQL، فاصله زمانی با `EXTRACT(EPOCH FROM b - a)` بر حسب ثانیه محاسبه می‌شود.
- برای نتیجه بر حسب ساعت، مقدار ثانیه بر `3600.0` تقسیم می‌شود. برای نتیجه بر حسب روز، مقدار ثانیه بر `86400.0` تقسیم می‌شود.
- تقسیم اعشاری، گردکردن، نوع تاریخ و منطقه زمانی باید مطابق SQL مرجع حفظ شوند.
- تلرانس ارزیابی حداکثر یک درصد است.
- LLM، UI و Serializer عدد را دوباره محاسبه یا گرد نمی‌کنند.
- SQL، نتیجه، Snapshot، Scope و `query_id` هر عدد منتشرشده ثبت می‌شوند.
- قرارداد کامل عددهای Ad hoc در `ISSUE-V3-02` باز است.

### ADR-V3-06 — Signal، وضعیت و تشدید

- **وضعیت:** پذیرفته‌شده.
- **ادغام‌شده از:** `ADR-07` و بخش وضعیت `ADR-09` نسخه ۲.
- وضعیت‌ها فقط `new`، `escalated` و `ongoing` هستند.
- Signal ابتدا به مالک KPI می‌رسد.
- رسیدن به آستانه یا عبور از آن در جهت نامطلوب، Signal را فعال می‌کند. مقایسه آستانه شامل تساوی است.
- اگر زمان نامطلوب بیشتر باشد و آستانه `warn` برابر چهار ساعت باشد، مقدار چهار ساعت یا بیشتر هشدار می‌دهد.
- رسیدن مستقیم به `crit` یا عبور از آن: مالک `new` و مدیر بالاتر `escalated` دریافت می‌کند.
- رسیدن به `warn` و سپس رسیدن به `crit`: مورد مالک `ongoing` می‌ماند و تاریخچه تشدید حفظ می‌شود.
- KPI سطح Workflow یا سازمان که به `warn` برسد یا از آن در جهت نامطلوب عبور کند، به مدیر ارشد تشدید می‌شود.
- مورد بدون تغییر معنادار دوباره `new` نمی‌شود.
- R5 فقط انحراف در جهت نامطلوب را Signal می‌داند.
- حداکثر پنج مورد نمایش داده می‌شود.
- Signalهای هم‌علت برای مدیر ارشد یک مورد هستند.
- KPI نوع `info` هشدار نمی‌سازد.

### ADR-V3-09 — انتشار مستقل و رفتار شکست

- **وضعیت:** اصل انتشار پذیرفته‌شده؛ Retry و Fallback باز است.
- **برگرفته از:** `ADR-14` نسخه ۲.
- گزارش معتبر هر مدیر مستقل منتشر می‌شود.
- شکست گزارش یک مدیر بر گزارش‌های معتبر مدیران دیگر اثر نمی‌گذارد. گزارش‌های معتبر حفظ و منتشر می‌شوند.
- اگر گزارش شکست‌خورده الزامی باشد، وضعیت نهایی اجرای روز `incomplete` است. این وضعیت گزارش‌های معتبر همان روز را حذف نمی‌کند.
- نبود API مدل نباید محاسبه عدد و JSON معتبر را متوقف کند.
- تعداد Retry، Timeout و Fallback در `ISSUE-V3-06` باز است.
