# الزام‌های رابط کاربری DIDRAH

این سند الزام‌های لازم برای پیاده‌سازی رابط کاربری را مشخص می‌کند. این سند درباره رنگ، فونت، چیدمان، نوع نمودار، ساختار صفحه یا سبک تعامل تصمیم نمی‌گیرد. تیم فرانت‌اند می‌تواند این موارد را طراحی کند، به شرط آن‌که الزام‌های این سند رعایت شوند.

منابع این سند، فایل‌های `architecture/structurizr/docs/` و `architecture/structurizr/adrs/` هستند. اگر بین منابع تضاد باشد، `docs/15-implementation-contract.md` مرجع است. قرارداد OpenAPI نیز مرجع جزئیات درخواست و پاسخ API است.

## ۱. مرز مسئولیت فرانت‌اند

- رابط کاربری باید داده مجاز را نمایش دهد و اقدام کاربر را به Backend API بفرستد.
- رابط کاربری نباید KPI، درصد، رتبه، روند، سیگنال، تشدید، SLA یا نتیجه تصمیم را محاسبه کند.
- رابط کاربری نباید عدد دریافتی را گرد یا باز‌محاسبه کند. قالب‌بندی عدد فقط زمانی مجاز است که مقدار را تغییر ندهد.
- رابط کاربری نباید به PostgreSQL، آرشیو فایل یا فایل‌های ورودی دسترسی مستقیم داشته باشد.
- رابط کاربری نباید نتیجه، عدد یا پاسخ جایگزین تولید کند.
- رابط کاربری نباید تصمیم سازمانی را اجرا کند. تأیید و اجرای اقدام، مسئولیت انسان است.
- مرورگر قابل اعتماد نیست. Backend API باید هویت و مجوز هر درخواست را بررسی کند.
- پنهان‌کردن یا غیرفعال‌کردن یک کنترل در UI، کنترل امنیتی نیست.
- رابط کاربری نباید اطلاعات محرمانه یا اطلاعات ورود را در وضعیت کلاینت، فضای ذخیره‌سازی، لاگ یا telemetry نگه دارد.

مرجع: `docs/01-purpose-and-scope.md`، `docs/04-security-and-trust.md`، `docs/07-quality-attributes.md`، `docs/09-web-application-components.md`، ADR-0005 و ADR-0010.

## ۲. الزام‌های عمومی

- فناوری رابط کاربری باید React 19، TypeScript و Vite باشد.
- همه رابط‌ها باید فارسی و راست‌به‌چپ باشند.
- منطقه زمانی کسب‌وکار `Asia/Tehran` است.
- ارتباط با Backend API باید از طریق HTTPS و JSON انجام شود.
- هر سه رابط باید فقط وضعیت موقت نمایش را در مرورگر نگه دارند.
- پس از تغییر کاربر، نقش یا محدوده، داده قدیمی محدوده قبلی باید پاک شود.
- خطا، ممنوع‌بودن دسترسی، نبود داده و در دسترس نبودن سرویس باید وضعیت‌های جدا و روشن داشته باشند.
- محتوای سؤال، تیکت و فایل آپلودشده باید «داده غیرقابل اعتماد» در نظر گرفته شود، نه دستور سیستم.
- telemetry رابط کاربری اختیاری است. در صورت فعال‌بودن، داده آن باید پاک‌سازی شود. خرابی telemetry نباید کار رابط را متوقف کند. telemetry نباید اطلاعات محرمانه، سند کامل یا داده محدودشده را ارسال کند.

مرجع: `docs/02-architecture-overview.md`، `docs/04-security-and-trust.md`، `docs/06-deployment-and-operations.md`، `docs/09-web-application-components.md` و ADR-0020.

## ۳. کاربران و رابط‌ها

| رابط | کاربران | کارکرد الزامی |
|---|---|---|
| دستیار گفت‌وگویی (`chatUi`) | مدیر ارشد، مدیر واحد، سرپرست تیم | نمایش گزارش و پاسخ محدودشده، دریافت سؤال و فایل، ثبت فرمان مدیر، نمایش وضعیت کار و بازبینی |
| داشبورد نقش‌محور (`dashboardUi`) | مدیر ارشد، مدیر واحد، سرپرست تیم | نمایش KPI، هدف، روند، جزئیات، تصمیم و اقدام باز در محدوده مجاز |
| اتاق کنترل جریان کار (`workflowUi`) | فقط مدیر ارشد | نمایش WF1 تا WF3، SLA مرحله، گلوگاه، تشدید و تصمیم در انتظار |

این سه رابط در یک Web Application اجرا می‌شوند. آن‌ها نباید یکدیگر را فراخوانی کنند یا وضعیت کسب‌وکار مشترک داشته باشند.

Backend API باید محدوده دقیق داده را تعیین کند. فرانت‌اند نباید از عنوان شغلی یا جایگاه سازمانی، مجوز اضافه استنتاج کند.

مرجع: `docs/09-web-application-components.md`، ADR-0005 و ADR-0007.

## ۴. رفتار مشترک API و کارهای غیرهم‌زمان

- برای کار غیرهم‌زمان، رابط کاربری باید `job_id` را از Backend بگیرد و وضعیت کار را از API پیگیری کند.
- حالت در صف یا در حال اجرا باید با وضعیت «در انتظار» نمایش داده شود.
- فقط نتیجه ذخیره‌شده و اعتبارسنجی‌شده می‌تواند «آماده» نمایش داده شود.
- شکست اجرا یا اعتبارسنجی باید صریح نمایش داده شود. UI نباید نتیجه قبلی یا حدسی را جایگزین کند.
- UI فقط باید وضعیت و نتیجه مجاز کاربر جاری را نمایش دهد.
- فرمان تکراری باید از شناسه و داده idempotency صادرشده توسط سرور استفاده کند.
- نام دقیق endpoint، payload، status code و روش پیگیری وضعیت باید از قرارداد OpenAPI گرفته شود و نباید در UI حدس زده شود.

مرجع: `docs/05-runtime-flows.md`، `docs/09-web-application-components.md` و ADR-0019.

## ۵. دستیار گفت‌وگویی

این رابط باید قابلیت‌های زیر را داشته باشد:

- نمایش گزارش‌های مدیریتی مجاز؛
- ارسال سؤال محدودشده؛
- نمایش `query_id` کنار پاسخ عددی موردی؛
- آپلود سند؛
- نمایش خطای پردازش فایل نامعتبر یا پشتیبانی‌نشده؛
- نمایش کارت تصمیم معتبر برای بازبینی؛
- ثبت سه اقدام انسانی «تأیید»، «ویرایش» و «رد» برای کارت تصمیم؛
- ارسال فرمان‌های `CloseSignal`، `ReferSignal`، `SetManagerPriority`، `ChangeKpiTarget` و `ChangeKpiThreshold`؛
- نمایش وضعیت کار و وضعیت بازبینی.

ویرایش کارت تصمیم باید یک job جدید برای اصلاح ایجاد کند. فقط کارت تأییدشده می‌تواند وارد رکورد تصمیم شود.

مرجع: `docs/05-runtime-flows.md`، `docs/09-web-application-components.md`، `docs/16-domain-model.md` و ADR-0023.

## ۶. داشبورد نقش‌محور

این رابط باید قابلیت‌های زیر را داشته باشد:

- نمایش KPI، هدف، روند، تصمیم و اقدام باز در محدوده مجاز؛
- ارسال فیلتر و درخواست جزئیات به Backend؛
- نمایش مشخصات نمودار و داده‌ای که Backend تولید کرده است؛
- نمایش جزئیات بار کاری مستقیم فقط زمانی که Backend آن را مجاز اعلام کند؛
- نمایش وضعیت روشن برای پاسخ ممنوع یا در دسترس نبودن داده؛
- پاک‌کردن داده قدیمی پس از تغییر محدوده.

UI نباید داده نمودار، KPI یا جزئیات را محاسبه یا اصلاح کند. UI باید نوع نمودار اعلام‌شده در مشخصات را رعایت کند. ظاهر، چیدمان و سبک ترسیم در اختیار تیم فرانت‌اند است.

مرجع: `docs/09-web-application-components.md` و `docs/11-background-worker-components.md`.

## ۷. اتاق کنترل جریان کار

این رابط باید قابلیت‌های زیر را داشته باشد:

- نمایش وضعیت WF1، WF2 و WF3؛
- نمایش SLA مرحله، گلوگاه، مالک، تشدید و تصمیم در انتظار؛
- ارسال درخواست جزئیات مجاز؛
- نمایش وضعیت ممنوع یا در دسترس نبودن داده؛
- پاک‌کردن داده قدیمی محدوده پس از خطای مجوز.

این رابط فقط برای مدیر ارشد است. UI نباید مالک مرحله، SLA، گلوگاه یا تشدید را محاسبه یا در کد ثابت کند. Backend باید این مقادیر را برگرداند.

مرجع: `docs/09-web-application-components.md`، `docs/15-implementation-contract.md`، ADR-0006 و ADR-0007.

## ۸. معناهایی که UI باید درست نمایش دهد

### ۸.۱. گزارش مدیریتی

- هر گزارش حداکثر پنج `item` دارد.
- وضعیت `item` یکی از `new`، `ongoing` یا `escalated` است.
- `data_issues` باید جدا از سیگنال‌های کسب‌وکار نمایش داده شود.
- KPI وابسته به داده غایب `null` است، نه `0`.
- گزارش `restated` باید از گزارش `as_reported` قابل تشخیص باشد.
- نسخه منتشرشده گزارش تغییرناپذیر است. نسخه جدید نباید جای نسخه قبلی را بگیرد.
- وضعیت روز `incomplete` نباید گزارش معتبر سایر مدیران را پنهان کند.
- نبود متن تولیدشده مدل نباید گزارش دارای اعداد معتبر را نامعتبر نشان دهد.

### ۸.۲. سؤال موردی

- هر عدد در پاسخ باید به `value` و `query_id` معتبر متصل باشد.
- `query_id` باید کنار پاسخ قابل مشاهده باشد.
- `refused_out_of_scope` یعنی داده وجود دارد، اما خارج از محدوده کاربر است.
- `data_unavailable` یعنی داده در منابع سیستم نیست، وارد سامانه نشده است یا هنوز نرسیده است.
- این دو وضعیت نباید با یک پیام یکسان نمایش داده شوند.
- در حالت `data_unavailable`، UI نباید عدد حدسی یا منبع خارجی نشان دهد.

### ۸.۳. سیگنال

- وضعیت سیگنال برای هر گیرنده مستقل است.
- UI باید وضعیت، مالک، تاریخچه تشدید و دلیل تشدید دریافتی از Backend را نمایش دهد.
- UI باید گروه‌بندی سیگنال‌های هم‌علت را که Backend برمی‌گرداند حفظ کند.
- UI نباید سیگنال بسازد، وضعیت آن را تغییر دهد یا تشدید را محاسبه کند.

### ۸.۴. تصمیم و پیگیری

- کارت تصمیم باید KPI هدف، مقدار هدف، بازه اندازه‌گیری ۳ تا ۵ روز، KPI محافظ و حد آن را نشان دهد.
- UI باید تأیید صریح مدیر را پیش از ثبت تصمیم بگیرد.
- نتیجه پیگیری می‌تواند `improved`، `worsened`، `no_change` یا `too_early` باشد.
- نتیجه باید تحقق معیار موفقیت، روش و فرض‌ها، سطح اطمینان و عوامل مزاحم را نشان دهد.
- اگر اثر قابل تفکیک نیست، متن باید بگوید: «اثر قابل جدا کردن نیست».
- UI نباید تصمیم را اجرا، پیام را خودکار ارسال یا کارت را خودکار تأیید کند.

### ۸.۵. تغییر تنظیمات

- UI باید نسخه پیشنهادی (`candidate`) را از نسخه فعال (`active`) جدا نشان دهد.
- UI باید وضعیت اعتبارسنجی و زمان فعال‌سازی را نمایش دهد.
- تغییر معتبر در KPI، سازمان یا اولویت مدیر در D+1 فعال می‌شود، نه همان روز.
- UI نباید تنظیمات را اعتبارسنجی نهایی یا فعال کند.

مرجع این بخش: `docs/05-runtime-flows.md`، `docs/07-quality-attributes.md`، `docs/14-stores-and-contracts.md`، `docs/15-implementation-contract.md`، `docs/16-domain-model.md`، ADR-0004، ADR-0006، ADR-0009، ADR-0010، ADR-0014، ADR-0015، ADR-0017 و ADR-0023.

## ۹. داده فردی و محدوده دسترسی

- `customer_id` فقط داخلی است و نباید نمایش داده شود.
- شهر و KPI تجمیع‌شده شهر می‌توانند نمایش داده شوند، اگر Backend آن‌ها را مجاز برگرداند.
- ظرفیت تیم فقط به‌صورت تجمیع‌شده نمایش داده می‌شود.
- UI نباید حضور و غیاب فردی، رتبه‌بندی افراد یا سرزنش فردی را نشان دهد.
- جزئیات فردی فقط برای بررسی بار کاری مستقیم سرپرست و با مجوز صریح Backend قابل نمایش است.

ماتریس کامل دسترسی هنوز نهایی نشده است. تا زمان نهایی‌شدن آن، UI نباید دسترسی هیچ نقش را فراتر از پاسخ Backend فرض کند.

مرجع: `docs/04-security-and-trust.md`، `docs/07-quality-attributes.md` و ADR-0005.

## ۱۰. نگاشت مقدارهای قراردادی

مقدارهای قراردادی باید در درخواست، پردازش پاسخ و وضعیت برنامه بدون تغییر استفاده شوند. UI می‌تواند برای آن‌ها برچسب فارسی روشن نشان دهد. این نگاشت باید یک‌جا و ثابت تعریف شود.

| مفهوم | مقدارهای قراردادی |
|---|---|
| وضعیت item یا سیگنال | `new`، `ongoing`، `escalated` |
| وضعیت پاسخ سؤال | `refused_out_of_scope`، `data_unavailable` |
| نوع مسئله داده | `missing`، `late_arrival`، `duplicate` |
| نسخه گزارش | `as_reported`، `restated` |
| جهت اثر تصمیم | `improved`، `worsened`، `no_change`، `too_early` |
| وضعیت روز ناقص | `incomplete` |

مقدارهای دیگری که Backend یا OpenAPI مشخص می‌کند نیز باید با همین قاعده نگاشت شوند. UI نباید مقدار قراردادی جدید بسازد.

## ۱۱. موارد باز

- محصول و روش احراز هویت هنوز مشخص نشده است.
- ماتریس نهایی دسترسی نقش‌ها و داده فردی هنوز مشخص نشده است.

این سند برای این دو مورد تصمیم جدید نمی‌گیرد. پیاده‌سازی باید آن‌ها را قابل پیکربندی نگه دارد و از قرارداد Backend پیروی کند.

مرجع: `docs/04-security-and-trust.md`، `docs/08-risks-and-open-issues.md` و `docs/09-web-application-components.md`.
